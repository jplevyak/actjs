# Monorepo guide

How to keep the frontend and backend in sync, and how to release them
together, when both halves of an actjs app live in one repo.

This document is workflow-focused. For the underlying framework
mechanisms it relies on (manifest pinning, class versioning,
generated `.d.ts`), see [`PLAN.md`](./PLAN.md) — in particular
Phases 4 and 6.

## What "in sync" means

Four distinct things people conflate:

1. **Type sync** — the FE's TS types match what the BE accepts/returns
   *at compile time*.
2. **Schema sync** — the FE's runtime validators match the BE contract
   *at runtime*.
3. **Version sync** — the FE knows which *class versions* it expects
   to talk to.
4. **Deploy sync** — both halves go out together, or with planned
   overlap for in-flight clients.

A lot of "it worked on my machine" breakage is people conflating (1)
with (4): the types match in the IDE, so deploys must be fine. They
aren't. Old browser tabs exist. Mobile apps cache. CDNs serve stale
bundles for minutes.

## What actjs gives you for free

These framework-level mechanisms make most of the workflow below
mechanical rather than disciplined:

- **Class versions are immutable.** A published `Cart@1.4.2` cannot
  change. A new BE deploy never edits behavior an old FE depends on.
- **Sticky-by-default activation.** New BE versions don't yank the rug
  from actors already created against older versions.
- **Deprecation ≠ deletion.** Marking a version deprecated hides it
  from *new* resolutions but leaves it queryable for clients pinned to
  a manifest that references it.
- **Manifest sha is observable.** Every request carries the manifest
  the client expected; the server logs and gauges it.
- **`actctl codegen` is the single source of truth.** Class TS source
  → `.d.ts` + `manifest.json`. No hand-maintained type files on both
  sides.
- **Client-pinned manifests.** Bundles ship with the manifest sha they
  were built against and send it as `X-Actjs-Manifest` on every call;
  the server uses it directly instead of re-resolving.

## Repo layout

```
actjs-app/
├── apps/
│   ├── server/                  # actjs server entry + config
│   └── web/                     # Svelte or React frontend
├── packages/
│   ├── classes/                 # all actor class TS source
│   │   ├── Cart/
│   │   │   ├── 1.0.0.ts
│   │   │   └── 1.4.2.ts         # versions live as files
│   │   ├── Ledger/
│   │   │   └── 1.0.0.ts
│   │   └── package.json
│   ├── client-types/            # GENERATED by actctl codegen
│   │   ├── index.d.ts
│   │   └── manifest.json        # { sha256, resolved: { Cart: "1.4.2", ... } }
│   └── sdk-react/               # thin wrapper over @actjs/client
├── .changeset/                  # changesets for coordinated bumps
├── turbo.json                   # task graph + caching
├── pnpm-workspace.yaml
└── package.json
```

Key invariants:

- `packages/classes/` is the **single owner of class source**. The
  server publishes from it on deploy; codegen reads from it on build.
- `packages/client-types/` is **always generated, never edited**. It's
  committed (so PRs are reviewable as diff) but `actctl codegen
  --check` fails CI if it's stale.
- `apps/web/` depends on `client-types/` and `sdk-react/`. It cannot
  reach into `packages/classes/` directly — enforced by lint
  (`eslint-plugin-boundaries`, Nx tags, or tsconfig path
  restrictions).
- Workspace tool: pnpm + Turborepo. Nx is fine too. Don't use yarn 1.

## The release flow

The hard rule: **the BE deploys first, the FE deploys second, and the
only edits in between releases are additive on the BE side.**

```
1. Developer edits packages/classes/Cart/2.0.0.ts  (new major version)
2. turbo run codegen          → regenerates packages/client-types/
3. turbo run typecheck        → apps/web fails if it used a removed method
4. turbo run test             → contract tests against an in-process server
5. Open PR. CI runs steps 2-4 plus integration tests against compose.
6. Merge → CD pipeline:
   a. Publish new class versions to the BE (immutable, additive).
   b. Wait for BE health check confirming new versions are queryable.
   c. Deploy the new FE bundle (pinned to the new manifest sha).
   d. Old FE clients in the wild keep working because their pinned
      manifest still references versions present on the BE.
```

The ordering matters because between (a) and (c) the BE is serving
*both* the old and new versions. There is never a moment when an FE
in the wild can request a class version that doesn't exist on the
BE.

For the "release everything together" feel without giving up the
safety: a **single Changeset** bumps both `apps/server` and
`apps/web` in the same PR with the same version. Changesets
generates linked release notes; CD treats the bump as one deploy
with the BE/FE ordering above as an internal implementation detail.

## What counts as a breaking BE change

| Change                              | Class semver bump | Old FE keeps working? |
| ----------------------------------- | ----------------- | --------------------- |
| Add a new handler                   | minor             | Yes                   |
| Add an optional field to an event   | minor             | Yes                   |
| Add a required field to a handler   | major             | Yes (old version still runs) |
| Remove a handler                    | major             | Yes (until old ver deprecated) |
| Change return-type semantics        | major             | Yes (until old ver deprecated) |
| Rename a field                      | major             | Yes (until old ver deprecated) |
| Fix a bug in an existing handler    | patch             | See below             |

The patch case is the only subtle one. Sticky-by-default means:

- *New* actors created with the bumped class get the patched behavior.
- *Existing* actors stay pinned to whatever version they were created
  with. They get the patch only when explicitly migrated
  (`actctl actor migrate <id> <newVersion>`).

The rule of thumb is **never edit a published version's behavior in
place.** Bump and let the old one keep running. Storage is cheap;
mysterious production breakage is not.

## CI guardrails

These keep teams honest without ceremony:

1. **`actctl codegen --check`** — the generated `.d.ts` and
   `manifest.json` match what's committed. Fails on stale.
2. **`actctl publish --dry-run`** — would each new class version
   publish succeed? (Version not already present; declared deps
   resolve.)
3. **API snapshot test** — serialize the OpenAPI doc and the
   `manifest.json`; assert byte-exact against committed snapshots.
   Reviewers see schema changes in PR diff form.
4. **Boundary lint** — `apps/web/` cannot import from
   `packages/classes/`. Enforced by eslint or tsconfig path
   restrictions.
5. **Migration replay test** — for every PR touching a class with a
   `migrate()` function, replay against a fixture corpus of
   historical snapshots.
6. **Forbid `Name` (unversioned class refs)** in `apps/web/` source.
   `actjs/no-unversioned-class` lint rule.
7. **Manifest-in-use check before deprecate** — `actctl manifest
   in-use` reports which client manifest shas are still being sent in
   production. Deprecating a class version while a non-trivial
   fraction of clients pin to it fails CI on the deploy that flips
   the `deprecated` flag.

## Day-to-day developer loop

```
# Start everything: BE, Valkey, PG, hot-reloading codegen
pnpm dev

# In another shell: classes/ changes are picked up automatically
$EDITOR packages/classes/Cart/1.5.0.ts

# Typescript in apps/web/ updates within a second of saving a class
# (codegen --watch is part of `pnpm dev`).

# Run the relevant tests for what you changed
turbo run test --filter='...[HEAD^]'
```

Local dev uses `pin: 'latest'` on the SDK so the FE talks to the
just-published pre-release versions without rebuilding. Production
builds use the embedded manifest sha.

## When you're not in a monorepo

The same patterns work in polyrepo with two additions:

- The BE publishes a typed SDK package (`@your-org/api-client`) to a
  private registry on every release. That package contains exactly
  what `client-types/` would have contained in a monorepo.
- The FE depends on it by exact semver. The "FE deploys after BE"
  rule becomes "FE bumps its `api-client` dep after the BE publishes."

The cost is one extra publish step per iteration and a slower local
loop (no shared workspace). Monorepo is materially better for actjs's
call pattern because the FE's *type* world is generated from the BE's
*class source* — keeping that loop inside one workspace removes a
publish step from every change.

## What this doc deliberately does not cover

- **Mobile clients (iOS/Android).** Same rules apply: pin a manifest
  sha, BE never edits in place, deprecate with a long window. But the
  release cadence is different (App Store review, slow user
  upgrades), so the deprecation window must be measured in months,
  not days.
- **GraphQL-style "ask for what you want" partial responses.** actjs
  returns full handler results; if you need projection, do it on the
  server in the handler.
- **A/B testing of class behavior.** Run two minor versions and route
  by tag in your `auth()` hook returning a `Manifest` override. Not
  built into the framework.
